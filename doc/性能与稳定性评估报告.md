## 0. 执行摘要

### 0.1 一句话结论

**这套代码的"防御性"做得相当好（统一信封、绝不 reject 的请求层、正则安全闸、输出尾部窗口、定时器/监听清理全覆盖），但"边界控制"存在系统性缺口：`上限存在，却施加在错误的层级`——大文件在传输后才截断、diff 在主线程同步算完才判超限、写队列只有串行没有准入、脏状态只有读取没有写入、终端缓冲只在 rAF 活着的时候才排空。**这些缺口不会在常规点击中暴露，但会在"大文件 + 长会话 + 高频保存"的真实使用形态下集中爆发。

### 0.2 四个关注维度的直接回答

| 关注点 | 结论 | 关键依据 |
|---|---|---|
| **大文件查看/修改是否安全** | ❌ 有明确的**主线程锁死**风险（可达数分钟） | 2–8 MiB 文件整份经 HTTP+JSON 进入主线程后才 `split` 截断（`FileEditor.tsx:123-136`）；**`diff-model.ts:187/196` 把 `linesOf()` 写在循环条件里，整文件 diff 退化为 O(n²)**；每帧 `doc.toString()` + 全量比较；`highlightSelectionMatches()` 对全文扫描；diff 用 jsdiff 同步 Myers 且无 timeout |
| **事务处理是否会死锁** | ✅ **不存在死锁**（经完整调用链证明），但存在"队列雪崩"与"丢更新"两类真实缺陷 | `serialized` 全仓库仅 1 个调用点（`routes/git.ts:54`），30 个写方法、13 个读方法内部均不再入队 → 无嵌套。但写队列无准入、无超时、任务不可取消；`writeSettings` 完全没有串行化且临时文件名固定 |
| **长时间运行是否内存泄漏** | ⚠️ 无"引用泄漏"，但有 3 处**无界增长** | 终端 `pendingWrite` 无上限且 rAF 在后台标签页暂停；`/run/output` 每轮 `chunks.join('')` 重建全文；项目树/提交列表/搜索结果全程无虚拟化，DOM 与行对象随规模线性增长 |
| **错误是否会导致崩溃** | ✅ 主链路不会崩（请求层不抛、宿主双保险），局部有崩溃点 | 3 处未校验外部字段直接调方法（`match.text.indexOf`、`diagnoseCommand.trim()`）；1 处 DOM API 未包 try（`releasePointerCapture`）；请求无超时导致业务标志位永久卡死 |
| **是否会造成数据破坏** | ⚠️ 有 2 处 | 推送目标取自过期响应 → 推到错误远端（`PushDialog.tsx:135-153/245-249`）；搁置用位置性 selector → 连点会弹出/删除错误的记录（`ShelfTab.tsx:157-160`） |

## 2. 架构与风险面地图

### 2.1 数据流总览

```
浏览器（主线程）                        宿主进程（Node，与 DSH 共用事件循环）
┌────────────────────────────┐          ┌──────────────────────────────────┐
│ WorkbenchServices（总线）   │          │ routes/index.ts  单前缀 /dsh-ide/api │
│   ├ settings / gitStatus   │  fetch   │   ├ fs.ts    ── fs-service      │
│   ├ invalidate 广播        │ ───────► │   ├ git.ts   ── git-read/git-write│
│   └ toast / selection      │  信封     │   │        └─ git-service(spawn) │
│                            │ {ok,val} │   ├ run.ts   ── run-service(spawn)│
│ feature（13 个，各自渲染）  │ ◄─────── │   ├ search.ts── search-service    │
│   └ lazy chunk（4 个）      │          │   └ settings-service（磁盘 JSON）  │
└────────────────────────────┘          └──────────────────────────────────┘
```

### 2.2 风险集中在四条链路

| 链路 | 数据量级 | 当前处理方式 | 风险 |
|---|---|---|---|
| **文件 → 编辑器** | 最大 8 MiB | 全量 JSON 传输 → 客户端截断 | A 组（4 项） |
| **文件 → 差异视图** | 单侧 2 MiB × 2 | 全量传输 → jsdiff 同步 → 全文高亮 → 渲染 2000 行 | A 组（3 项） |
| **Git 写操作** | 每仓库一条串行队列 | 串行但无准入、无超时、不可取消 | B 组（6 项） |
| **进程输出 → 面板** | 宿主 512 KiB 环形缓冲 | 轮询 + join 重建 + 客户端 256 KiB 尾窗 | C 组（3 项） |

### 2.3 一个容易被忽略的结构性事实

**主区视图与右侧栏是两个独立的 Workbench 实例，共用同一套 localStorage key**（`client/index.tsx:380-387` 创建两个组件、`426` 行 `keepMounted: true` 让右侧栏常驻）。

后果：
- `dsh-ide.layout.v1.<sessionId>` 与 `dsh-ide.editors.v2.<sessionId>` 被两个实例争抢写入 → 在右侧栏打开文件会把主区的标签集合覆盖掉；
- 两套 `WorkbenchServices` 各自 `loadSettings()` + `refreshGitStatus()`（`Workbench.tsx:128-131`）→ Git 状态请求翻倍；
- 两套 `CommandPalette` 各自挂全局 `keydown`（`CommandPalette.tsx:142`）→ `⌘J`/`⌘,` 同时作用两块工作台。

这不是性能问题，但它**放大了所有性能问题**（请求翻倍、订阅翻倍、轮询翻倍），因此列为 P1（§5.2 的 R-C12）。

## 3. 专项 A：大文件查看与修改

### A.1 打开链路：上限施加在错误的层级（P1，R-A1）

**位置**：`src/client/features/editor/FileEditor.tsx:123-142`、`src/host/services/fs-service.ts:35`、`src/host/routes/fs.ts:75-84`

**代码证据**

```ts
// fs-service.ts:35 —— 宿主允许读到 8 MiB
const MAX_READ_BYTES = 8 * 1024 * 1024

// FileEditor.tsx:123-136 —— 客户端拿到整份之后才判断是否过大
const result = await apiGet<ReadResponse>('/fs/read', { root: services.root, path })
...
const tooLarge = result.value.bytes > LARGE_FILE_BYTES            // 2 MiB
const text = tooLarge
  ? result.value.text.split('\n').slice(0, LARGE_FILE_PREVIEW_LINES).join('\n')  // 先 split 全文
  : result.value.text
```

**数据量与代价**（以 8 MiB / 约 20 万行的文件为例）

| 阶段 | 实际发生的分配 | 备注 |
|---|---|---|
| 宿主 `readFile` | 8 MiB Buffer + 8 MiB UTF-8 字符串 | `fs-service.ts:210-228` 先 `stat` 再读，无流式 |
| 序列化为 JSON 响应 | 约 8–10 MiB（转义膨胀） | `sendOk` → `JSON.stringify` |
| 浏览器 `response.json()` | 8 MiB 原始 body + 8 MiB 解码字符串 | 峰值已约 3 倍文件体积 |
| `split('\n')` | 20 万个行字符串对象 + 数组 | 每行至少 40 字节对象头 → 额外 8–16 MB |
| `slice(0,2000)` 之后 | 只剩约 80 KB | **99% 的分配被立即丢弃** |

**触发条件**：打开任何 2 MiB 以上的文件。5–8 MiB 时用户会感到 1–3 秒白屏 + 内存尖峰；接近 8 MiB 且行数极多（如 minified 单行文件 8 MB）时 `split` 只产生 1 行，反而快——**最坏情况是"中等长度行 + 大量行"**，因为 `split` 成本随行数线性增长。

**修复方案（推荐 A：宿主侧支持 headLines）**

```ts
// fs-service.ts —— readTextFile 增加 options
export async function readTextFile(
  root: string,
  input: string,
  options: { maxBytes?: number; headLines?: number } = {},
): Promise<{ text: string; bytes: number; version: string; truncated: boolean }> {
  const target = await resolveWithin(root, input)
  const info = await stat(target.absolute)
  // ...
  const limit = options.maxBytes ?? MAX_READ_BYTES
  // headLines 存在时用流式读，读到 N 行即停：
  if (options.headLines !== undefined) {
    const stream = createReadStream(target.absolute, { encoding: 'utf8' })
    let text = ''
    let lines = 0
    for await (const chunk of stream) {
      text += chunk
      lines = (text.match(/\n/g) ?? []).length
      if (lines >= options.headLines) { stream.destroy(); return { text: text.slice(0, text.lastIndexOf('\n')), bytes: info.size, version: versionOf(info), truncated: true } }
    }
  }
  // ...
}
```

客户端把判断提前到请求参数：

```ts
// FileEditor.tsx
const statInfo = await apiGet<{ bytes: number }>('/fs/stat', { root, path })
const tooLarge = (statInfo.ok ? statInfo.value.bytes : 0) > LARGE_FILE_BYTES
const result = await apiGet<ReadResponse>('/fs/read', {
  root, path, ...(tooLarge ? { headLines: LARGE_FILE_PREVIEW_LINES } : {}),
})
```

**收益**：打开 8 MiB 文件的峰值内存从约 40 MB 降到约 1 MB，耗时从秒级降到毫秒级。

**验证方法**：造一个 6 MiB / 12 万行的 `.ts` 文件，用 Chrome Performance 录制"打开文件"操作；修复前 main thread 有 1–3 s 长任务，修复后应无可感知长任务，且 `Memory` 面板 Heap 峰值差 < 5 MB。

### A.2 每次击键的全量比较与待修复的输入延迟（P1，R-A2）

**位置**：`src/client/lazy/editor-kernel.ts:139-152`、`FileEditor.tsx:215-219`

**代码证据**

```ts
// editor-kernel.ts:139-152 —— rAF 合并，但每次仍是全量 toString
const scheduleChange = (): void => {
  if (frame !== null) return
  frame = window.requestAnimationFrame(() => {
    frame = null
    options.onChange(view.state.doc.toString())      // 全量字符串拷贝
  })
}

// FileEditor.tsx:215-216 —— 全量比较
onChange: (text) => {
  setDirty(text !== savedTextRef.current)            // O(n) 字符串比较
```

**影响**：2 MiB 文档下每次停顿产生一次 2 MiB 字符串分配 + 一次 2 MiB 逐字符比较（V8 在指针不等时会逐字符比较，最坏 O(n)）。用户体感是"打字有轻微粘滞"，且 GC 压力上升（每秒可达数十 MB 短命对象）。

**为什么不是 P0**：rAF 合并把频率压到 60 Hz，且单次成本约 1–3 ms（2 MiB 文档），尚在可接受范围。**但如果 A.1 的 headLines 修复没做、文档到 8 MiB，单次会到 5 ms 以上并开始掉帧。**

**修复方案**

```ts
// editor-kernel.ts —— 只回传"是否有改动 + 长度"，取值改为惰性
let pendingDirty = false
const scheduleChange = (): void => {
  pendingDirty = true
  if (frame !== null) return
  frame = window.requestAnimationFrame(() => {
    frame = null
    if (!pendingDirty) return
    pendingDirty = false
    options.onDirtyChange?.(true)      // 脏标记：不需要全文
  })
}
// 新增：仅在保存/预览时才取全文
getValue: () => view.state.doc.toString(),
```

`FileEditor` 侧：`onDirtyChange` 直接 `setDirty(true)`；`savedTextRef` 比较改为"保存成功后把 `versionRef` 作为已保存锚点"，不再做字符串比较。Markdown 预览改为在 `previewText` 防抖回调里取一次 `kernel.getValue()`。

**验证方法**：在一个 1.5 MiB 的 `.ts` 文件里连续输入 200 个字符，用 Performance 面板看 scripting 时间；修复前约 250–400 ms，修复后应 < 80 ms。

### A.3 `highlightSelectionMatches()` 在超大文档上是全文扫描（P1，R-A3）

**位置**：`src/client/lazy/editor-kernel.ts:169`（扩展装填处）

**代码证据**

```ts
// editor-kernel.ts —— 与 search 一起装进扩展列表
search({ top: true }),
highlightSelectionMatches(),        // 每次选区变化都要找全文同样的词
```

**机制**：`@codemirror/search` 的 `highlightSelectionMatches` 在选区变化、文档变化、视口变化时都会启动一次 `RegExpCursor`，扫描范围是**整个文档**（它要标出视口外的匹配数）。2 MiB 文档的单词量可达 20 万，每次移动光标或双击选词都会跑一次全文正则扫描。

**实测特征**（CodeMirror 官方 issue 与社区报告的典型值）：1 MiB 文档上单次约 8–25 ms；2 MiB 上约 20–60 ms。用户体感是"双击选词后卡一下"、"拖选时掉帧"。

**修复方案（三选一）**

```ts
// 方案 1（最小改动）：限制 maxMatchLength，并接受"超长文档不启用"
highlightSelectionMatches({ maxMatchLength: 200 }),

// 方案 2（推荐）：按文档规模动态启用
const extensions = [
  ...(docLength < 512 * 1024 ? [highlightSelectionMatches({ maxMatchLength: 200 })] : []),
]

// 方案 3（体验最好）：保留功能但把搜索范围限制在视口
// 自定义 ViewPlugin：仅对 view.visibleRanges 内的文本做匹配与装饰
```

**验证方法**：打开 2 MiB 的 `.ts`，双击一个常见词（如 `const`），用 Performance 面板记录一次事件处理耗时：修复前 20–60 ms，修复后 < 5 ms。

### A.4 切换标签重建编辑器两次，且撤销历史必然丢失（P2，R-A4）

**位置**：`FileEditor.tsx:198-255`、`EditorArea.tsx:424-437`

**代码证据**

```tsx
// FileEditor.tsx:198 —— 内核 effect 依赖 status
useEffect(() => {
  if (status !== 'ready' || hostRef.current === null) return undefined
  ...chunk.create({ doc: savedTextRef.current, ... })     // 用「上一个文件」的内容创建
}, [path, status])

// FileEditor.tsx:251-255 —— 另一个 effect 在 path 变化时把 status 打回 loading
useEffect(() => {
  setConflict(null)
  setStatus('loading')
  void load('open')
}, [load])
```

**时序**：从 A 切到 B 时，同一渲染周期内 `status` 仍是 `'ready'` 而 `path` 已变成 B → 内核 effect 先用 **A 的内容**创建一个 `EditorView`；随后第二个 effect 提交 `setStatus('loading')` → 上一个 effect 清理、销毁视图；B 读完后 `status='ready'` → 再创建一个。

**后果**：
1. 每次切标签 = 2 次 `EditorView` 构造 + 1 次全量 `/fs/read`（`EditorView` 构造对 2 MiB 文档约 30–80 ms）；
2. A 的内容闪一下；
3. 撤销历史、滚动位置、选区全部丢失（`EditorArea` 只渲染活动标签，没有 keep-alive）。

**修复方案**

```tsx
// 让内核 effect 只依赖 path，内容由独立 effect 注入
useEffect(() => {
  if (hostRef.current === null) return undefined
  const host = hostRef.current
  let alive = true
  let kernel: EditorKernel | null = null
  void loadLazyChunk<EditorChunk>('editor-kernel').then((chunk) => {
    const created = chunk.create({ parent: host, path, doc: '', readOnly, ... })
    if (!alive) { created.destroy(); return }
    kernel = created
    kernelRef.current = created
    created.setValue(savedTextRef.current)     // 内容就绪后注入
  })
  return () => { alive = false; kernelRef.current = null; kernel?.destroy() }
}, [path])                                    // 不再依赖 status
```

若要保留撤销历史，需要 `EditorArea` 层做 keep-alive（对最近 N 个标签保留 kernel，非活动者 `display: none`）。

**验证方法**：打开 A、B 两个文件，来回切换 10 次，在 Performance 面板统计 `EditorView` 构造次数：修复前 20 次，修复后 0 次（视图复用）。

### A.5 差异计算：主线程同步 Myers，且字符级 diff 无全局预算（P1，R-A5）

**位置**：`src/client/features/git/diff-model.ts:214-225`、`:135-166`、`src/client/lazy/diff-kernel.ts:17-19`、`src/common/diff-source.ts:21`

**代码证据**


**代价模型**

| 场景 | 代价 |
|---|---|
| 2 MiB 文本、两侧 4 万行、改动 30% | `diffLines` 的 Myers 约 `O(N·D)`，D≈1.2 万 → 约 10⁸ 量级比较，**主线程 3–15 秒** |
| 2 MiB 文本、每行 ≤2000 字符、1000 对修改行 | 字符级 diff 累计 10⁹ 量级 → **再叠加 2–8 秒** |
| minified 单行 2 MiB | `MAX_CHAR_DIFF_LINE` 生效 → 快（这条保护是有效的） |

**关键事实**：`MAX_DIFF_BYTES = 2 MiB`（`diff-source.ts:21`）确实在上限内才允许计算，但 2 MiB 本身已经远超 jsdiff 的舒适区。`DiffView.tsx:78` 的 `MAX_DIFF_RENDERED_ROWS = 2000` **只限制渲染，不限制计算**——计算早已在 `computeDiffRows` 里完成。

**修复方案（三层）**

```ts
// 第 1 层：给 jsdiff 传预算（jsdiff 9 支持 timeout / maxEditDistance）
// diff-kernel.ts
import { diffLines, diffChars } from 'diff'
const resources = { timeout: 1500, maxEditDistance: 400 }
export default {
  diffLines: (left: string, right: string) => diffLines(left, right, resources),
  diffChars: (left: string, right: string) => diffChars(left, right, resources),
}

// 第 2 层：入口按"行数 × 字节"双重限流，超限直接走已有 too-large UI
// diff-model.ts
const MAX_DIFF_TOTAL_LINES = 20_000
export async function computeDiffRows(left, right, options) {
  const leftLines = linesOf(left)
  const rightLines = linesOf(right)
  if (leftLines.length + rightLines.length > MAX_DIFF_TOTAL_LINES) {
    throw new DiffTooLargeError()      // DiffView 捕获后 setState({ kind: 'too-large' })
  }
  // ...
}

// 第 3 层：字符级 diff 加全局预算
let charBudget = 2_000_000        // 单次差异视图共享的字符预算
// buildRows 内：
if (charBudget >= left.length + right.length) {
  charBudget -= left.length + right.length
  const chars = chunk.diffChars(left, right)
  // ...
} else {
  rows.push({ kind: 'modified', ..., leftSegments: [{ text: left, changed: true }], rightSegments: [{ text: right, changed: true }] })
}
```

**中长期**：`diff-kernel` 已是独立 chunk，改用 `new Worker(new URL('./diff-kernel.js', import.meta.url), { type: 'module' })` 的成本可控，可彻底消除主线程阻塞。宿主 `/asset/` 路由已支持下发 chunk（`asset.ts`），Worker 加载路径可用同一 URL。

**验证方法**：构造两侧各 2 MiB、改动 30% 的文件对，在 Git 面板点击该文件：修复前页面冻结数秒（可用 `setTimeout` 心跳检测到 > 2 s 的空档），修复后应在 1.5 s 内出现结果或"差异过大"提示。

### A.5b 最严重：`linesOf()` 被写在 `for` 循环条件里，复杂度退化为 O(n²)（P0，R-A5b）

**位置**：`src/client/features/git/diff-model.ts:187`、`:196`（`linesOf` 定义在 `:74-82`）

**代码证据**

```ts
// diff-model.ts:186-201 —— 注意循环的「条件表达式」
if (change.added === true) {
  for (let offset = 0; offset < linesOf(change.value).length; offset += 1) {
    const line = rightLines[rightIndex] ?? ''
    rightIndex += 1
    rows.push({ kind: 'added', leftNumber: null, rightNumber: rightIndex, left: '', right: line })
  }
  continue
}
for (let offset = 0; offset < linesOf(change.value).length; offset += 1) {
  //                                      ^^^^^^^^^^^^^^^^^^^^ 每次迭代都重新切一遍
  const line = leftLines[leftIndex] ?? ''
  leftIndex += 1
  rightIndex += 1
  rows.push({ kind: 'equal', leftNumber: leftIndex, rightNumber: rightIndex, left: line, right: line })
}

// diff-model.ts:74-82 —— linesOf 每次调用都 split 全文，且常常再 slice 复制一次
function linesOf(text: string): string[] {
  if (text === '') return []
  const lines = text.split('\n')
  return lines[lines.length - 1] === '' ? lines.slice(0, -1) : lines
}
```

**为什么这是全报告最严重的一处**

`offset < linesOf(change.value).length` 里的 `linesOf(...)` **不是一次求值，而是每次循环迭代都求值**。因此对一个包含 n 行的变更块，循环体执行 n 次，`linesOf` 被调用 n 次，每次 `split('\n')` 都要遍历 n 个字符位置并生成 n 个字符串，再（通常）`slice` 复制出一个新数组。

| 变更块规模 | `linesOf` 调用次数 | 累计字符串处理量 | 结果 |
|---|---|---|---|
| 1 000 行 | 1 000 | 约 10⁶ 次 | 用户会感到"卡一下"（约 30–80 ms） |
| 10 000 行 | 10 000 | 约 10⁸ 次 | 数秒冻结 |
| 50 000 行（整文件新增，2 MiB 完全可达） | 50 000 | **约 2.5×10⁹ 次** | **主线程锁死数十秒到数分钟，界面完全无响应** |
| 同时内存 | 每次至少 2 个 5 万元素数组 | 累计分配 TB 级 | GC 持续全速运行，进一步拖慢 |

**最容易触发的日常场景**（不是极端构造）：

- 新增一个文件后查看它的 diff（`change.added === true` 的块 = 整个文件）——**任何 1 万行的新文件都会让界面冻结数秒**；
- 首次提交的仓库、`git add -N` 后的整文件比较；
- 大段重排/格式化后的文件（大块 equal / added）；
- 从远端拉入一个此前不存在的文件后查看历史差异。

**这是纯粹的实现疏漏**：同一个函数的 `:131-132` 已经用了正确写法（先 `const xxxLines = linesOf(...)` 再迭代）。只需两行改动。

**修复方案**

```ts
// 修复：循环前求值一次
if (change.added === true) {
  const addedLines = linesOf(change.value)
  for (let offset = 0; offset < addedLines.length; offset += 1) {
    const line = rightLines[rightIndex] ?? ''
    rightIndex += 1
    rows.push({ kind: 'added', leftNumber: null, rightNumber: rightIndex, left: '', right: line })
  }
  continue
}

const equalLines = linesOf(change.value)
for (let offset = 0; offset < equalLines.length; offset += 1) {
  // ...
}

// 更进一步（推荐）：把 linesOf 的结果按 change 缓存，整个 buildRows 只切一次
const cache = new Map<Change, string[]>()
const linesOfCached = (change: Change): string[] => {
  const hit = cache.get(change)
  if (hit !== undefined) return hit
  const lines = linesOf(change.value)
  cache.set(change, lines)
  return lines
}
```

**验证方法**：造一个 1 万行、2 万行的新文件（`seq 1 20000 > /tmp/new.txt` 后提交），在 Local Changes 里点击它的 diff：修复前界面冻结数秒（可用「拖动窗口标题栏是否跟手」判断），修复后应在 100 ms 内出结果。

**顺带修正一个相关误判**：`MAX_DIFF_RENDERED_ROWS = 2000` 只限制渲染行数，对本缺陷**完全无效**——O(n²) 发生在 `computeDiffRows` 内部，早于任何渲染上限。

## 4. 专项 B：事务处理与并发（死锁分析）

### B.1 核心结论：当前不存在死锁（已证明）

**问题**：Git 写操作按仓库串行排队，若"排队任务的内部又调用了排队"，就会自己等自己 → 永久死锁。

**证明过程**（不依赖关键字搜索，而是闭合调用图）：

1. **唯一入口**：全仓库 `serialized` 的调用点只有 1 处。

```ts
// src/host/routes/git.ts:54
const value = write !== undefined ? await serialized(repo, () => write(repo, body)) : await read(repo, body)
```

2. **写方法侧**：`git-write.ts` 的 30 个导出写方法（`stage`/`unstage`/`discard`/`restoreFrom`/`commit`/`checkout`/`createBranch`/`deleteBranch`/`deleteRemoteBranch`/`renameBranch`/`updateBranch`/`worktreeAdd`/`merge`/`rebase`/`cherryPick`/`revert`/`reset`/`tag`/`dropCommit`/`amendMessage`/`pushUpToHere`/`formatPatch`/`fetch`/`pull`/`push`/`defineRemote`/`stash`/`stashApply`/`stashPop`/`stashDrop`）内部**均不调用** `serialized`。它们的内部 helper 只有三个，且都只落到 `execGit`：
   - `run()`（`git-write.ts:39-43`）→ `execGit`
   - `trackingRemote()`（`git-write.ts:383`）→ `execGit`
   - `readPaths`/`readWorktreePath`/`readStashSelector` → 纯同步参数校验
3. **读方法侧**：`git-read.ts` 的 13 个读方法在 `git.ts:54` 的三元表达式里走 `else` 分支，**根本不进队列**。
4. **结论**：队列任务的闭包内不含 `serialized` 调用 → 无自锁。180 秒的 `push` 也不会把只读 `status` 排到同一队列，**"UI 状态刷新被长任务阻塞"这一具体担忧不成立**。

### B.2 但"潜在死锁"仍然存在：`serialized` 无重入保护（P0，R-B1）

**位置**：`src/host/services/git-service.ts:84-105`

```ts
export function serialized<T>(repo: string, task: () => Promise<T>): Promise<T> {
  const previous = queues.get(repo) ?? Promise.resolve()
  const next = previous.then(task, task)     // ← 若 task 内部再调 serialized(repo, ...)，等待的正是自己
  const settled = next.catch(() => undefined)
  queues.set(repo, settled)
  // ...
  return next
}
```

**为什么定为 P0**：这不是"当前有 bug"，而是"**一处误改即全局冻结**"。`serialized` 是 `export` 的公共 API、注释里没有任何"禁止嵌套"警告、也没有运行期检测。任何人后续给某个写方法加一行 `await serialized(repo, () => execGit(...))`（看起来完全合理，甚至像是"更安全"），该仓库的所有写操作与所有后续写操作将**永久**挂起：

- 没有超时（`execGit` 的超时只覆盖子进程，不覆盖队列等待）；
- 不会报错（Promise 永不 settle，HTTP 请求一直挂着直到宿主断开连接）；
- 无法自愈（`queues` 里的 `settled` 永远 pending，后续任务全部排在它后面）。

**修复方案**

```ts
// 1) 加运行期检测：队列上下文用 AsyncLocalStorage 标记
import { AsyncLocalStorage } from 'node:async_hooks'
const queueContext = new AsyncLocalStorage<string>()

export function serialized<T>(repo: string, task: () => Promise<T>): Promise<T> {
  if (queueContext.getStore() === repo) {
    // 同仓库嵌套 = 必然死锁，立刻抛错而不是挂起
    return Promise.reject(new GitError('GIT_QUEUE_NESTED', `serialized() is re-entered for ${repo}`))
  }
  const previous = queues.get(repo) ?? Promise.resolve()
  const next = previous.then(() => queueContext.run(repo, task), () => queueContext.run(repo, task))
  // ...
}

// 2) 加等待超时（防止未来任何形式的悬挂）
const QUEUE_WAIT_TIMEOUT_MS = 120_000
```

至少必须做的**零风险改动**：在函数注释里写明"任务内部禁止再次调用本函数，否则同仓库永久死锁"。

**验证方法**：写一个临时用例 `serialized('/tmp/x', () => serialized('/tmp/x', async () => 1))`，修复前永不返回，修复后立刻 reject。

### B.3 写队列无准入控制：连点即雪崩（P1，R-B2）

**位置**：`routes/git.ts:54`、`git-service.ts:90-105`、`git-write.ts:383`（网络命令超时）

**现象**：所有写操作无条件排队。用户连点 5 次 Push，队列里就有 5 个各自最长 180 秒的网络任务 → 第 5 个要等 15 分钟。而宿主的 HTTP server（Node 默认 `server.requestTimeout = 300s`，由宿主配置决定）会先断开连接，**但队列里的任务仍在跑**——用户看到"失败"，重试，队列继续变长。

**修复方案**

```ts
// git-service.ts —— 队列增加"同签名去重 + 深度上限"
const pendingSignatures = new Map<string, Promise<unknown>>()
const MAX_QUEUE_DEPTH = 8

export function serializedOnce<T>(repo: string, signature: string, task: () => Promise<T>): Promise<T> {
  const key = `${repo}\u0000${signature}`
  const existing = pendingSignatures.get(key)
  if (existing !== undefined) return existing as Promise<T>     // 同一条命令重复点击 → 复用同一个 Promise
  // 队列深度检查 + 计数
  // ...
}
```

在 `git.ts` 里用 `method + 参数摘要` 作为 signature（例如 `push:origin:main`）。同一签名在途时，后续请求直接返回第一个的结果（"幂等合并"），这正是 IDEA 的行为。

**验证方法**：对 `/git/exec` 连发 5 个 `method:'push'` 请求，观察 `ps` 中的 git 进程数：修复前 5 个串行、修复后 1 个 + 4 个复用结果。

### B.4 写队列任务不可取消（P1，R-B3）

**位置**：`git.ts:54`、`git-service.ts:114-211`

`execGit` 的 `AbortSignal` 完全没有接入——客户端 `apiPost` 也没传 signal（`client/features/git/api.ts:169-171`）。后果：

- 用户点了 `fetch`（最长 180 s）后切走、关闭面板、切会话，任务照跑到底；
- 没有任何办法取消一个已经排队的写任务；
- 应用退出时 `stopAllRuns` 只处理运行进程，不处理 git 子进程。

**修复方案**：`apiPost` 支持 `signal`，`git.ts` 把 `request` 的 `'close'` 事件转换为 `AbortController.abort()`，`execGit` 增加 `signal` 参数（`signal.addEventListener('abort', () => child.kill('SIGTERM'))`）。注意：**取消写操作有数据风险**（`git commit` 中途被杀可能留下 index 状态），建议只对只读与网络类命令（`fetch`/`pull`/`push` 的传输阶段）开放取消。

### B.5 文件保存的乐观锁是"检查-写入"两步，且版本令牌精度有限（P1，R-B4）

**位置**：`fs-service.ts:85`（令牌生成）、`:240-286`（写入流程）

```ts
// fs-service.ts:85 —— 版本令牌 = mtimeMs + size
function versionOf(info: { mtimeMs: number; size: number }): string {
  return `${info.mtimeMs}:${info.size}`
}

// fs-service.ts:240+ —— stat → 校验 → 写临时文件 → rename（无锁）
```

**两个缺陷**

1. **精度**：`mtimeMs` 是毫秒。某些文件系统（HFS+、部分网络挂载、容器 overlay）时间戳精度是 1 秒。若外部进程在同一秒内写入**且文件大小不变**（原地替换等长内容），`versionOf` 完全相同 → 乐观锁失效 → 覆盖外部改动。
2. **无锁的并发写**：两个并发保存（用户连按 `⌘S` + 自动保存）都通过校验、都写各自临时文件、都 rename → 后 rename 者胜；更糟的是若两者用**同一临时文件名**就相互破坏。当前 `writeTextFile` 使用了唯一临时名（见下），所以不会互相破坏，但"后写覆盖前写"仍存在——这是可接受的语义（最后一次保存胜出），但**若两次保存的内容不同（一次是用户手改、一次是自动保存的旧快照），用户会看到"我明明改了却回到旧内容"**。

```ts
// fs-service.ts:254-266 —— 实际使用的是唯一临时名，这一点是正确的
const temporary = `${absolute}.${String(process.pid)}.${String(Date.now())}.tmp`
```

**修复方案**

```ts
// 1) 令牌纳入纳秒与内容哈希前缀（成本可控：只在前 4 KiB 上算）
import { createHash } from 'node:crypto'
function versionOf(info: Stats, head: Buffer): string {
  return `${info.mtimeNs ?? info.mtimeMs}:${info.size}:${createHash('sha1').update(head).digest('hex').slice(0, 12)}`
}

// 2) 保存路径上串行化（同一路径的写入排队）
const writeQueues = new Map<string, Promise<unknown>>()
export function writeTextFile(...) { return serializedByPath(absolute, () => doWrite(...)) }
```

**验证方法**：并发发出两个 `/fs/write`（不同文本、同一 `expectedVersion`）：修复前两个都返回 ok（后者胜），修复后第二个应返回 `STALE_FILE`。

**为什么这是问题**

```ts
// 3) 客户端加 300ms 合并（拖拽弹窗尺寸、连续改字号时只发最后一次）
```

**更彻底的方案**：`/settings` 支持 PATCH 语义（只提交变更字段），从根上消除"全量覆盖"造成的丢更新。

### B.7 Git 超时只杀直接子进程，远端助手会变成孤儿（P2，R-B6）

```ts
// 超时分支：

```

**验证方法**：对一个慢远端执行 `git fetch`，在 5 秒后强制超时（临时把 `NETWORK_TIMEOUT` 调小），用 `ps -ef | grep git-remote` 检查是否残留。

### B.10 推送目标可能来自过期响应：提交被推到用户没选的远端（P1，R-B12）

**位置**：`PushDialog.tsx:135-153`（`reload`）、`:245-249`（`runPush`）

```ts
// PushDialog.tsx:135-153 —— 无请求序号、无取消
const reload = useCallback(async (): Promise<void> => {
  if (root === '') return
  const result = await readPushPreview(root, preferredRemote)
  if (!result.ok) { setPreview(null); ...; return }
  setPreview(result.value)
  setErrorText('')
  setScope(BRANCH_SCOPE)
  setCommitFiles(new Map())
}, [preferredRemote, root])

// PushDialog.tsx:245-249 —— 推送目标取自可能过期的 preview
const result = await push(root, {
  force,
  ...(pushTags ? { tags: tagsScope } : {}),
  ...(preview === null ? {} : { remote: preview.remote }),
})
```

**机制**：`reload` 的依赖是 `preferredRemote`，用户在下拉里连续切换远端（A→B）会产生两个并发 `readPushPreview`。网络乱序时**先返回的响应后落地**，`preview.remote` 因此可能与用户最后选择的 `preferredRemote` 不一致。`runPush` 又直接使用 `preview.remote` 作为目标——**代码会被推送到错误远端**。

**这是"对外数据事故"级别**：推到错误远端后即使强推修正，也会在错误远端留下分支与提交，且可能触发他人的 CI/部署。窗口虽窄（需要快速切换远端后立刻点推送），但后果不可撤销。

**修复方案**

```ts
const seqRef = useRef(0)

const reload = useCallback(async (): Promise<void> => {
  if (root === '') return
  const seq = (seqRef.current += 1)          // 每次发起取号
  const result = await readPushPreview(root, preferredRemote)
  if (seq !== seqRef.current) return         // 已有更新的请求，丢弃本结果
  // ...
}, [preferredRemote, root])

const runPush = async (force: boolean): Promise<void> => {
  // 推送目标以「用户当前选择」为准，并在发起前校验 preview 与之一致
  const target = preferredRemote !== '' ? preferredRemote : preview?.remote ?? ''
  if (preferredRemote !== '' && preview !== null && preview.remote !== preferredRemote) {
    setErrorText(t('previewOutdated'))       // 提示「待推送内容已变化，请刷新」
    return
  }
  const result = await push(root, { force, ...(target === '' ? {} : { remote: target }) })
}
```

**验证方法**：在 DevTools 里对 `/git/exec` 的 `pushPreview` 响应加 1–3 秒随机延迟，快速切换远端 A→B 后立即推送；修复前观察 `git push` 的实际 argv（控制台会记录），修复后应始终为目标远端或直接拒绝。

### B.11 搁置（Stash）用位置性选择符 + 无重入守卫 → 会删错记录（P1，R-B13）

**位置**：`ShelfTab.tsx:103-125`（`run`）、`:152-180`（右键菜单）

```ts
// ShelfTab.tsx:103-125 —— run() 只设 busy，不检查、不拦截
const run = useCallback(async (action): Promise<void> => {
  setBusy(true)
  try { const result = await action(); /* ... */ }
  finally { setBusy(false) }
}, [...])

// ShelfTab.tsx:157-160 —— 菜单项直接执行，完全不看 busy
{ id: 'apply', label: t('unshelve'), run: () => void run(() => applyStash(root, item.selector)) },
{ id: 'pop',   label: t('popStash'), run: () => void run(() => popStash(root, item.selector)) },
{ id: 'drop',  label: t('dropStash'), danger: true, separatorBefore: true, run: () => askDrop(item) },
```

**机制**：stash 的选择符是**位置性**的（`stash@{0}`、`stash@{1}`）。用户在 `stash@{1}` 上连点两次 Pop：

1. 第一次 `git stash pop stash@{1}` → 成功，原 `stash@{1}` 消失，原 `stash@{2}` 递补为 `stash@{1}`；
2. 第二次仍针对字符串 `"stash@{1}"` 执行 → **弹出的是另一条搁置记录**（原本的 `stash@{2}`）。

`drop` 有二次确认框拦截，`apply`/`pop` 没有。注意：宿主的写队列会**串行**执行这两条命令（所以不是并发问题），但串行执行并不能避免"第二次指向了不同的记录"——**问题在于选择符是位置而非身份**。

**修复方案**

```ts
// 1) 用 hash 而非 selector 定位（git stash pop/apply 支持提交对象）
run: () => void run(() => popStash(root, item.hash))

// 2) 同时加不变量：busy 时拒绝新动作（用 ref，state 在同一帧内尚未更新）
const busyRef = useRef(false)
const run = useCallback(async (action) => {
  if (busyRef.current) return
  busyRef.current = true
  setBusy(true)
  try { /* ... */ } finally { busyRef.current = false; setBusy(false) }
}, [...])

// 3) 菜单项在 busy 时置灰
{ id: 'pop', label: t('popStash'), disabled: busy, run: ... }
```

**验证方法**：造 3 条 stash，在 `stash@{1}` 上快速连点两次 Pop：修复前第 2 次弹出的记录 `subject` 与第 1 次不同（`git stash list` 可验证）；修复后第 2 次被拒绝或作用于同一条（若第一次已删除则报错）。

## 5. 专项 C：长时间运行的内存与资源

### C.1 宿主侧：所有缓存都有上限，但有两处无界（P1/P2，R-C1 ~ R-C3）

| 对象 | 位置 | 上限 | 结论 |
|---|---|---|---|
| `queues` | `git-service.ts:68` | 队尾自删（`:99-102`） | ✅ 有界 |
| `repositoryCache` | `git-service.ts:76` | TTL 30 s + 64 条（超限整体 `clear`） | ✅ 有界 |
| `chunkCache` | `asset.ts:27` | 白名单只有 4 个 chunk | ✅ 有界 |
| `processes` / `buffers` / `children` | `run-service.ts:57/72/75` | 仅 `startRun` 时 `pruneFinished(20)` | ⚠️ 见 R-C1 |
| `knownRoots` | `workspace.ts:16` | **无上限、无 TTL** | ⚠️ 见 R-C2 |
| 搜索结果 | `search-service.ts:31` | `MAX_SEARCH_MATCHES = 2000` | ✅ 有界 |

**R-C1（P2）运行实例表的清理时机过于被动**

```ts
// run-service.ts:128-138 —— 只在 startRun 里调用 pruneFinished()
export function startRun(...): RunProcess {
  pruneFinished()          // 仅此处
  // ...
}
```

若用户连续启动 30 个实例、全部结束、再也不启动新的：`processes` 里保留 20 个（被裁剪）→ 实际有界。**但**：`disposeRun`（`:321`）只在客户端显式清理时调用，且客户端没有任何"自动清理已结束实例"的逻辑 → 20 个已结束实例的输出缓冲（每个 512 KiB）= 最多 10 MiB 常驻，直到下次启动。可接受，但建议加"实例结束 5 分钟后自动释放缓冲"的定时器（`timer.unref()`）。

**R-C2（P2）`knownRoots` 无上限**

```ts
// workspace.ts:16
const knownRoots = new Map<string, string>()
// :86 —— 只增不减（仅在根被删除时 delete）
```

键是会话的工作区根路径。单机插件场景下会话数量有限（几十个），实际膨胀风险低。但**没有 TTL 意味着根路径改名/移动后旧条目永久残留**，且每次命中仍会 `stat(cached)`（`:65`）—— 缓存只省了 `realpath`，没省 IO。建议：加 `MAX_KNOWN_ROOTS = 64` + 命中时按 LRU 淘汰；把 `stat` 校验改为 TTL（如 10 s）内跳过。

**R-C3（P1）`readOutput` 每轮重建全文**

```ts
// run-service.ts:187-191
function bufferTextOf(buffer: OutputBuffer): string {
  buffer.text = buffer.chunks.join('')      // 每次调用都 join 全部 chunk
  return buffer.text
}

// run-service.ts:202-218 —— 每次 HTTP 请求都调用
export function readOutput(id: string, offset: number) {
  // ...
  const text = bufferTextOf(buffer).slice(offset)   // 再 slice 一次
}
```

**代价**：运行中的进程每秒产生数百次输出 chunk 时，每个 chunk 都 `text = undefined`（`appendOutput` 里置空缓存）→ 每次轮询（RunPanel 800 ms + OutputPanel 1 s + RunningStatus 5 s）都 `join` 一次 512 KiB → 每秒约 1.25 次 × 512 KiB ≈ 640 KiB/s 的字符串分配，持续整个进程生命周期。**这是"在跑一天就分配 55 GB 短命字符串"量级的浪费**（虽然会被 GC 回收，但 GC 压力会体现为周期性卡顿）。

**修复方案**：增量返回。`readOutput` 直接按 offset 到 `chunks` 的字符区间取值，避免 join 全文：

```ts
export function readOutput(id: string, offset: number) {
  const buffer = buffers.get(id)
  if (buffer === undefined) return { text: '', bytes: 0, overflowed: false }
  // 只在 offset 落在已裁剪区间时才需要 splice/错误处理
  const text = sliceChunks(buffer.chunks, offset, buffer.bytes)
  return { text, bytes: buffer.bytes, overflowed: offset < buffer.startOffset }
}
```

或更简单：让 `appendOutput` 维护"已 join 的前缀"（`text` 只在 trim 时重建），并在 `chunks` 最后追加的 chunk 之后只 join 新增部分。

### C.2 客户端：三处无界增长（P0/P1）

**R-C4（P0）终端输出合并缓冲无上限，且出口在后台标签页被暂停**

**位置**：`TerminalPanel.tsx:284-299`、`:360-365`

```ts
let pendingWrite = ''
let writeFrame: number | null = null

/** 把攒下的输出一次写进终端。 */
const flushWrite = (): void => {
  writeFrame = null
  if (pendingWrite === '') return
  const data = pendingWrite
  pendingWrite = ''
  kernel?.write(data)
}

// 收帧循环内：
if (frame.type === 'output') {
  pendingWrite += frame.data                                   // 无上限累积
  if (writeFrame === null) writeFrame = window.requestAnimationFrame(flushWrite)
}
```

**为什么无界**：`requestAnimationFrame` 在 `document.hidden`（标签页切走 / 窗口最小化 / 系统锁屏）时被浏览器**暂停**——这是规范行为，不是异常。此时 `flushWrite` 永不执行，而 `for await (const frame of attached)` 循环**继续收帧**（宿主侧进程在跑，输出持续推送），`pendingWrite` 单调增长。

**量级**：一个输出 2 MB/s 的 dev server，在后台 8 小时 → 57 GB 字符串。即使只是切走 10 分钟，也有 1.2 GB。切回前台时 `kernel.write(data)` 一次性把全部内容交给 xterm 解析 → 又一次主线程冻结（可能触发崩溃或标签页 OOM）。

**注意**：`scrollback: 1000`（`terminal-kernel.ts:44`）只限制"已写入 xterm 的行"，对 `pendingWrite` 毫无作用。这是本项目最隐蔽的一处无界增长。

**修复方案**

```ts
/** 待写入缓冲的字符上限；后台标签页 rAF 暂停时必须靠它兜底。 */
const MAX_PENDING_CHARS = 256 * 1024

let pendingWrite = ''
let dropped = 0

const flushWrite = (): void => {
  writeFrame = null
  if (pendingWrite === '' && dropped === 0) return
  const data = pendingWrite
  pendingWrite = ''
  kernel?.write(data)
  if (dropped > 0) {
    kernel?.write(`\r\n\x1b[33m[省略 ${String(dropped)} 字符输出]\x1b[0m\r\n`)
    dropped = 0
  }
}

// 收帧处：
pendingWrite += frame.data
if (pendingWrite.length > MAX_PENDING_CHARS) {
  const cut = pendingWrite.length - MAX_PENDING_CHARS
  dropped += cut
  pendingWrite = pendingWrite.slice(cut)
}
if (writeFrame === null) {
  writeFrame = window.requestAnimationFrame(flushWrite)
  // 兜底：rAF 在后台不触发，用 setTimeout 保证后台也能排空（被节流到 ~1s 也没关系）
  window.setTimeout(flushWrite, 1000)
}
```

**R-C5（P1）项目树：全量重建 + 无虚拟化 + 重复排序（三个问题叠加）**

**位置**：`use-project-tree.ts:150-171`、`tree-model.ts:118-127`、`:140-153`、`:165-214`、`ProjectTree.tsx:159-160`、`:298`、`use-git-status.ts:64-71`


**三个叠加的放大因子**

1. **触发频率**：`rows` 的依赖里包含 `gitStatus`（Map）与 `isIgnored`（回调，依赖 `matcher`，依赖 `ignoredPaths`），而 `loadGitStatus` **每次广播都新建 Map/Set**（`services.ts` 内 `loadGitStatus` 的成功分支）。因此**每一次 git 状态刷新（250 ms debounce）都会重建整棵树**；每次保存、每次 git 操作都会触发刷新。
2. **单次成本**：对每个已展开目录 D，`visibleEntriesOf` 排序一次（`localeCompare` 带 `{numeric, sensitivity}` 选项，单次约 0.5–1 µs）→ 若展开 500 个目录、平均 40 个子项，单次重算约 500 × 40 log40 × 0.8 µs ≈ **100 ms**；再加上 `hasVisibleChildren` 导致的二次排序，约 **200 ms**。这发生在主线程，用户看到的是"保存后树卡一下"。
3. **渲染成本**：`renderRow` 是组件体内定义的普通函数，`EntryRowView` 没有 `React.memo` → 任意状态变化（选中行、键盘焦点、git 刷新）都重建 2000 行 × 每行 5–6 个 span + 内联 SVG ≈ **300–800 ms / 次**。

**修复方案（三步，按收益顺序）**

```ts
// 第 1 步（收益最大、改动最小）：把排序结果缓存进 DirectoryState
// data.ts —— fetchDirectory 里排序一次
return { status: 'ready', entries: sortEntries(entries), truncated }
// tree-model.ts —— visibleEntriesOf 只做过滤，不再 sort

// 第 2 步：hasVisibleChildren 复用已过滤结果，不重复计算
// 在 buildRows 内先算一次 const visible = visibleEntriesOf(...)，把 visible.length 传下去

// 第 3 步：行组件 memo 化 + 稳定回调
const EntryRowView = React.memo(function EntryRowView(props) { ... })
// 父组件传 row + 稳定 dispatcher，而不是每行新建闭包：
onSelect={tree.selectRow}  onToggle={tree.toggleRow}  // 这两个在 use-tree-navigation 里已是稳定 useCallback
```

**若要做到"保存后树不卡"**：还需要切断 `gitStatus` → `rows` 的重算链。最直接的做法是**让 git 状态只影响行渲染、不影响行构建**——把手色的计算下移到行组件内（`EntryRowView` 自己 `useSyncExternalStore` 或接收 `statusOf(path)` 的取值结果），`rows` 的依赖里去掉 `gitStatus`/`isIgnored`（`showIgnored` 变化时才需要重算）。

**R-C11（P2）一次写操作触发最多 3 次完整的 `git status`**

**位置**：`LocalChanges.tsx:117-122`、`:174-199`（关键 `:187-191`）、`services.ts:351-358`

```ts
// LocalChanges.tsx:187-191 —— run() 内先自己刷新一次

setRevision((previous) => previous + 1)
services.refreshGitStatus()     // ② 250ms 后外壳再 readStatus
services.invalidate()

// LocalChanges.tsx:122 —— 又订阅了状态广播 → ③ 广播回来再 refresh 一次
useEffect(() => services.subscribeGitStatus(() => void refresh()), [refresh, services])
```

**代价**：一次「暂存」= 3 次全量 `git status`（每次 4 个 git 进程，见 `git-read.ts` 的 `status` 实现：`status --porcelain` + `ls-files --others` + `ls-files --ignored` + `branch`）。大型仓库单次 30–200 ms，因此一次点击产生 3 倍进程与 3 倍 IO，且第 3 次的结果与第 1 次相同。

**修复方案**：`run()` 内不要自己 `refresh()`，改为只 `services.refreshGitStatus()` 并依赖订阅回调统一刷新（单一数据源）；`ShelfTab.tsx:92/117-119` 同样处理。

**R-C13（P2）Git 控制台记录只限条数、不限单条大小**

**位置**：`console-store.ts:27`、`:66-69`

```ts
const MAX_ENTRIES = 200
// ...
entries = [...entries, { ...entry, id: sequence, time: timestampOf(new Date()) }].slice(-MAX_ENTRIES)
```

`execGit` 允许 `stdout` 到 16 MiB（`git-service.ts:15`），而 `recordGitConsole` 把 `stdout`/`stderr` **原样**存进模块级数组。`git fetch`/`git log`/`git format-patch` 的输出可达数 MB → 200 条 × 数 MB 可达数百 MB 常驻，且每次 `recordGitConsole` 都要 `[...entries]` 复制整个数组（浅拷贝 200 个引用倒是便宜，但 `notify()` 会触发 Console 页签重渲染并渲染全部输出）。

**修复方案**：每条记录对 `stdout`/`stderr` 各截断到 64 KiB，并在末尾追加 `\n… (已截断，原长 N 字节)`；Console 渲染端再按需展开（点击某条时才展示完整内容——但完整内容已不保留，改为"提示用户可在终端执行同一命令"）。

**R-C14（P2）任意文件保存都会让所有历史页签重取 diff**

**位置**：`HistoryTab.tsx:121`、`:157-161`

```ts
// HistoryTab.tsx:121 —— 全局 invalidate 广播 → 全量重读文件历史
useEffect(() => services.subscribeInvalidate(() => void loadCommits()), [loadCommits, services])

// HistoryTab.tsx:157-161 —— selected 是 re-find 出来的新对象
const source = useMemo<DiffSource | null>(() => {
  if (selected === null) return null
  return { kind: 'commits', from: selected.parents[0] ?? EMPTY_TREE, to: selected.hash, path }
}, [path, selected])
```

**机制**：`invalidate()` 是全局广播（保存文件、暂存、回滚都会发）。每次广播 → `loadCommits()` 重读 200 条 → `commits` 新数组 → `selected` 重新 `find` 得到**新对象引用** → `source` 变成新对象 → `DiffView` 的取数 effect 依赖 `source` → **重新拉两侧完整文本 + 重跑 jsdiff + 重跑语法高亮**。

**后果**：保存一个与历史页签**完全无关**的文件，会让每个打开的历史页签各产生 2 次大请求 + 1 次主线程 diff 计算。打开 3 个历史页签时放大 3 倍，并与 `autoSave: true`（每 500 ms 一次）叠加成持续的请求风暴。

**修复方案**：

```ts
// 1) source 只依赖身份字段，不依赖对象引用
const source = useMemo<DiffSource | null>(() => {
  if (selectedHash === '') return null
  return { kind: 'commits', from: parentHash, to: selectedHash, path }
}, [parentHash, path, selectedHash])

// 2) subscribeInvalidate 按路径过滤（只对与本文件相关的变更重读）
useEffect(
  () => services.subscribeInvalidate((changed) => {
    if (changed === undefined || changed === path) void loadCommits()
  }),
  [loadCommits, path, services],
)
```

（`services.invalidate(path?)` 已经支持传路径，`FileEditor` 保存时也确实传了 `path`，所以过滤是可行的。）

**后果（准确表述，不夸大）**：

- 默认 `autoSave: true` + 500 ms 延迟，**大多数情况下改动会先落盘**，所以"改一半切标签就丢"只在以下场景发生：

```ts
    const index = previous.tabs.findIndex((item) => serializeTabKey(item.key) === previous.active)
    if (index < 0 || previous.tabs[index]?.dirty === dirty) return previous
    const tabs = previous.tabs.map((item, i) => (i === index ? { ...item, dirty } : item))
    return { ...previous, tabs }
  })
}, [])
// <ActiveRender ... onDirtyChange={handleDirtyChange} />
```

同时给 `FileEditor` 加 `key={activeKey}`，让每个标签拥有独立实例（当前同一实例复用导致切标签时内核两次创建，见 R-A4）。

**验证方法**：关闭自动保存 → 编辑 → 标签应出现圆点 → 点击关闭应弹出确认 → 选"取消"改动保留、选"放弃并关闭"改动丢弃。

**R-D7（P0）保存请求在途时继续输入，最后一笔改动被"洗白"**

**位置**：`FileEditor.tsx:156-195`（关键 `171-179`）

```ts
const text = kernel.getValue()               // t0 时刻的内容
const result = await apiPost<{ version: string }>('/fs/write', { ..., text, expectedVersion: versionRef.current })
if (result.ok) {
  versionRef.current = result.value.version
  savedTextRef.current = text                // ← 回退到 t0
  setDirty(false)                            // ← 无条件清脏
  services.invalidate(path)
  services.refreshGitStatus()
  return
}
```

**时序**：

1. t0：`save()` 取到 text₀，发出请求；
2. t0–t1：用户继续输入 → `onChange` → `setDirty(text₁ !== savedTextRef.current)` → `dirty = true`，自动保存 effect 排一个 500 ms 定时器；
3. t1：请求返回 ok → `savedTextRef = text₀`，`setDirty(false)`；
4. t1+500 ms：定时器触发 `save()`，但 `dirty === false` 时**该 effect 的依赖没变，不会重排定时器**（`:301-309` 的 `if (!settings.autoSave || !dirty || readOnly) return undefined`）；
5. 结果：text₁ 那段输入**永远不落盘**，界面显示"已保存"。

**触发概率**：写入慢时显著提高——大文件（A.1 的 5–8 MiB）、网络盘、宿主繁忙、或 `expectedVersion` 冲突导致多一次 `/fs/read` 往返（`:181-189`）。

**修复方案**

```ts
const text = kernel.getValue()
const result = await apiPost(...)
if (result.ok) {
  versionRef.current = result.value.version
  savedTextRef.current = text
  // 只有"当前内容仍是提交时的那份"才算干净
  const current = kernelRef.current?.getValue()
  if (current === undefined || current === text) {
    setDirty(false)
  } else {
    // 期间有新输入：保持脏，并立刻把新内容排进下一轮保存
    setDirty(true)
    pendingResaveRef.current = true
  }
  // ...
} finally {
  savingRef.current = false
  if (pendingResaveRef.current) { pendingResaveRef.current = false; void save() }
}
```

同时把 `save()` 的早退分支（`:158` 的 `savingRef.current` 判断）改为"标记待重存"而不是静默 return：

```ts
if (kernel === null || readOnly) return
if (savingRef.current) { pendingResaveRef.current = true; return }
```

**验证方法**：在 DevTools 里把网络限速为 Slow 3G，输入 "abc" 后立刻再输入 "def"，等保存完成后检查磁盘文件：修复前文件只有 "abc"，修复后应为 "abcdef"。

### 6.4 宿主侧错误处理评价（做得好，记录以保持）

- `execGit`：`stdout` 16 MiB / `stderr` 4 MiB 双上限，超限立刻 kill 并回稳定错误码 `GIT_OUTPUT_TOO_LARGE`；`spawn` 的同步抛错、`error` 事件、`close` 事件、超时四条路径都覆盖，且用 `settled` 保证只 settle 一次。
- `readJsonBody`：流式累加，超 32 MiB 立刻 reject，不会先撑爆内存；`JSON.parse` 在 try 内并转成 `BodyError`。
- `respondFsError`：把 `StaleFileError`/`BodyError`/`FileTooLargeError`/`WorkspaceError`/errno 全部映射成稳定码与合适 HTTP 状态。
- `resolveWithin`：`realpath` 校验 + 最近存在祖先回退 + 根目录/家目录拒绝，边界校验是扎实的。
- `reveal-service`：`detached: true` + 5 s 超时 + `timer.unref()`，`xdg-open` 驻留问题处理正确。

### 6.5 数据破坏类缺陷（不属于崩溃，但后果更重）

这类缺陷不会让界面报错，而是**安静地把操作作用到错误的对象上**，因此比崩溃更危险。详见 §4 的 B.10 / B.11：

| ID | 缺陷 | 用户可感知的后果 |
|---|---|---|
| R-B12 | 推送目标来自可能过期的 `pushPreview` 响应 | 提交被推送到用户在 UI 上并未选择的远端 |
| R-B13 | 搁置记录用 `stash@{n}` 位置选择符 + 无重入守卫 | 连点 Pop 会弹出另一条搁置记录；该记录可能包含他人的未提交改动 |

两者的共同特征是：**操作对象应当用"身份"（hash/远端名）而不是"位置或派生值"来标识**。修复都只涉及几行代码（请求序号 + 目标校验、`item.hash` + `busyRef`），但收益是消除不可撤销的数据事故。

## 10. 结语

这套插件在**"接口规范化"与"资源生命周期"**两个维度上是同类项目中的上乘水平：统一的 `{ok, value}` 信封、永不 reject 的客户端请求层、宿主侧的异常双保险、正则安全闸、输出尾部窗口、定时器与监听的全覆盖清理、契约化的服务总线——这些都不是随手能写出来的，它们把"崩溃"这类最坏情况挡在了门外。

真正的问题全部集中在同一个思维盲区上：**上限与保护都已经想到、都写了，但施加在了"错误的一层"**——

- 大文件想保护，却把截断放在传输之后；
- 差异想保护，却只限制渲染行数而不限制计算（更有一处把 `linesOf()` 写进了循环条件，把 O(n) 变成 O(n²)）；
- 写队列想保护，却只做了串行而没有准入与超时；
- 脏状态想保护，却只写了读取端而没有写入端；
- 终端想保护，却把唯一的排空出口放在了会暂停的 rAF 上。

因此修复成本远低于问题数量所示：**第 1 批的 8 个小改动（约 1 天）即可消除全部 5 个 P0 与 4 个 P1**，第 2 批的 6 项能把主要卡顿压到不可感知。剩下的 P2/P3 可以按迭代节奏清理，不构成上线阻塞。

最后提醒两点（也是本报告最想强调的）：

1. **R-A5b 的修复只需两行，但它一个人就贡献了"打开新文件就冻结"的全部体验伤害**。如果只做一件事，就做这个。
2. **R-B1 的"潜在死锁"虽当前不可触发，但它是唯一一个"一旦发生就不可自愈、且无任何报错"的缺陷**。哪怕只做一件事，也请在 `serialized()` 的注释与实现里加上"禁止嵌套"的显式约束。
